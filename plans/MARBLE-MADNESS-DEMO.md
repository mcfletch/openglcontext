---

A modern re-interpretation of the 1984 Atari/Amiga game **Marble Madness**: an
aerial ¾-view time-trial where the player rolls a reflective PBR marble through a
**procedurally generated** maze of ramps, drops, bumpers, and moving mechanisms to
reach the finish before a per-level timer runs out. It is a **scene package** in
the mould of the sibling [forest-demo](../../forest-demo) — the generic simulation
and rendering live in `OpenGLContext`, and the package supplies the level
generator, the marble/game rules, the HUD, and the art.

The demo exists to exercise, end to end, machinery the engine already has but has
never combined into a playable game: the [physics engine](PHYSICS-COLLISION.md)
(dynamic sphere, materials, triggers, joints/drives, kinematic movers) driving
[PBR](PBR-MATERIALS.md) + [runtime IBL](RUNTIME-IBL.md) reflective surfaces under
[shadow maps](SHADOW-MAPPING.md).

**Build order:** basic playable gameplay first (roll → generated track → finish
before the timer), then progressively add the "bits" — ramps/boosts, mechanisms,
reflective-material variety, polish. The phasing in §8 reflects this.

## 1. Design goals

- **Fixed-offset follow camera.** One camera, no camera controls: a **perspective**
  view that looks at the marble from a **fixed offset** (a high ¾ angle evoking
  Marble Madness, though faithful isometric replication is not a goal) and tracks it.
  The *only* input is the four steering keys.
  - **On a fall, the camera holds on the last square.** When the marble leaves the
    track and starts to drop into the void, the camera stops following it and
    **stays looking at the last track square the marble was on**, until it respawns
    there. (During a legitimate airborne jump — see below — the camera keeps
    following the marble through the arc.)
- **Spin-to-steer control.** Holding an **arrow key imparts spin** (angular
  velocity) to the marble in that direction *for as long as it is held* — the spin
  impulse is **re-applied on every key-repeat / frame the key is down**, not once
  per press. Friction with the surface then converts that spin into rolling motion,
  so the player steers indirectly, with momentum — the defining feel of the
  original. **How much the spin actually moves the marble depends on the
  marble↔surface friction coefficient** (§7): high-μ pairings (rubber on stone) grip
  and translate spin into motion; low-μ pairings (steel on ice) slip, so the marble
  spins in place and coasts. A small direct linear assist keeps it responsive; the
  spin:assist ratio is a tunable.
- **Real jumps.** The marble is a real rigid body, so enough speed into an upward
  ramp launches it into a **ballistic arc** — it can clear gaps and land further
  along. This must *not* be mistaken for falling off (see §5, track-presence).
- **Procedurally generated levels.** A **pseudo-random generator** lays out each
  level's track (a connected path of tiles from start to finish, with branches,
  drops, and gaps), seeded so a run is reproducible. Hand-authored levels remain
  possible through the same piece vocabulary, but generation is the primary source.
- **Time trial.** Each level has a countdown timer shown **top-right**. Reach the
  **finish** trigger before it hits zero; running out ends the run (lose).
- **Everything is reflective PBR.** Marbles and surfaces render through the PBR path
  under image-based lighting so a steel/chrome marble mirrors its surroundings.
  Multiple **marble materials** (steel, chrome, glass, rubber, wood, ice) differ in
  *both* look (metallic/roughness/transmission) and feel
  (friction/restitution/mass).
- **Surfaces and mechanisms affect motion:** ramps add speed; walls and hard
  landings kill most of it; rubber bumpers return energy; spring traps, elevators,
  and rotating arms push the marble (some always running, some marble-triggered).
- **Fall-off recovery, with a penalty delay.** Falling off respawns the marble on
  the ground at the **track square where it fell off**, speed reset — not a full
  restart. Respawn is **not immediate**: a fixed **penalty delay** elapses first
  (camera held on that square, timer still counting) so a player cannot game the
  system by deliberately dropping off the edge to kill unwanted momentum — doing so
  always costs time.
- **Reset.** A key aborts the current run and returns to the level start.

### Non-goals (v1)

Networking, scoreboards/persistence, a level-editor UI, audio, gamepad support,
soft/deformable marbles, camera controls. Follow-ups may add sound and a gamepad
axis mapping.

## 2. What the engine already provides (reused, not rebuilt)

The demo is mostly **assembly** — most notably, **a complete rigid-body engine
already ships**, so the marble's gravity, sphere collision, friction, restitution,
rolling, and ballistic jumps are all existing behaviour. Concrete APIs it builds on:

**Physics** (`OpenGLContext/physics/`, see [PHYSICS-COLLISION.md](PHYSICS-COLLISION.md)):

- `physics.demo.DemoScene` — keeps a scenegraph and a `PhysicsWorld` in lockstep;
  `add_sphere(radius, position, color, dynamic, mass, material='rubber', velocity)`,
  `add_box(...)`, `add_mesh_body(geometry, shape, ...)`, `add_trigger_box(...)`,
  `material(name)`, `scene_graph(extra=...)`, `advance(dt)`. Backbone of every
  `tests/physics_*.py` demo and the template for the marble scene.
- `physics.model` — the OMI data model: `Motion` (`type` DYNAMIC/STATIC/KINEMATIC,
  `mass`, `linearVelocity`, `angularVelocity`, `linear/angularDamping`,
  `gravityFactor`, `quadraticDrag`), `Material`
  (`staticFriction`/`dynamicFriction`/`restitution`), `Trigger`, `Joint` +
  `JointLimit` + `JointDrive`, `Gravity` (directional or point). `MATERIAL_PRESETS`
  already ships `wood`/`metal`/`rubber`/`ice`.
- `PhysicsWorld` (`physics/world.py`) — per-body SoA arrays exposed as views:
  `world.position`, `world.orientation`, `world.linear_velocity`,
  `world.angular_velocity`, `world.awake`, indexed by body index; `world.wake(i)`,
  `world.add_trigger_listener(fn)`, `world.add_joint_constraint`, `world.add_body`.
  Fixed-timestep accumulator (`advance` → interpolation `alpha`, `writeback`).
- `PhysicsBody` node (`scenegraph/physicsbody.py`) — binds `Motion`/`Collider`/
  `Trigger` to a `Transform`; after registration exposes `body.index`/`body.world`,
  so per-frame control reads/writes `body.world.linear_velocity[body.index]`, etc.
- `physics.cookery.cook_shape(points, indices, strategy, dynamic)` — arbitrary mesh
  → collision shape (convex hull / primitive fit / trimesh).
- Triggers fire through `world.add_trigger_listener` / `dispatch_trigger` — the
  basis for finish lines, boost pads, spring traps, and level portals.

**Rendering** (see [PBR-MATERIALS.md](PBR-MATERIALS.md), [RUNTIME-IBL.md](RUNTIME-IBL.md)):

- `scenegraph/pbrmaterial.py::PBRMaterial` (metallic/roughness + the KHR extension
  stack: specular, ior, clearcoat, transmission, volume, …) drops straight into an
  `Appearance.material` slot; rendered with an audited Cook-Torrance BRDF.
- **IBL is shipped and needs no external asset**: `passes/ibl.py` (`IBLProbe`,
  `resolve_ibl_mode`, `OPENGLCONTEXT_IBL=full`) builds irradiance + prefiltered-
  specular + BRDF-LUT from a **procedural studio cube**, so metals reflect a real
  environment out of the box. For a richer sky, `scenegraph/hdrbackground.py::
  HDRBackground` loads a CC0 Poly Haven `.hdr` (`loaders/hdri.py`) as the skybox
  *and* registers it as the IBL radiance map.
- Directional **shadow maps** (`passes/shadowmap.py`), `passes/bloom.py`, and
  `passes/transmission.py` (screen-space, for glass) available through the core
  FlatPass. GPU instancing (`passes/instancing.py`) for repeated tiles/props.

**Context / loop / input** (templates: [`tests/physics_navigate.py`](../tests/physics_navigate.py),
`OpenGLContext/bin/terrain_view.py`):

- `testingcontext.getInteractive()` → `BaseContext`; override `OnInit`/`OnIdle`.
  `OnIdle` computes a clamped `dt`, steps the scene, writes the camera, and calls
  `triggerRedraw(1)`. Unlike the physics *demos*, this loop **always redraws every
  frame** — it does not gate on `DemoScene.advance()` returning `False` (body
  sleep). Gravity acts on the marble continuously and the countdown clock changes
  every frame, so an update is always needed; the sleep/settle optimization those
  demos use does not apply here.
- Held-key steering uses `addEventHandler('keyboard', name=k, state=1, function=...)`
  (key-down, re-emitted by key-repeat, with a `HOLD` window bridging repeat delay);
  one-shot actions (reset, material cycle) use `'keypress'`.
- Camera is a `move.viewplatform.ViewPlatform` on `context.platform`
  (`setPosition`, `.quaternion`). We write it every frame from the camera target and
  the fixed offset, after unbinding the default movement manager
  (`movementManager.unbind(self)`) so nothing fights our camera.

## 3. New engine additions (small, generic, land in `OpenGLContext`)

Kept minimal and reusable so they belong in the engine, not the scene package:

1. **Impulse API on `PhysicsWorld`** — the world exposes velocity *views* but no
   public "apply impulse". Add:
   ```python
   world.apply_impulse(i, j)            # linear:  v += j / mass ; wake(i)
   world.apply_angular_impulse(i, l)    # angular: w += invI · l ; wake(i)
   ```
   Steering, ramp boosts, bumpers, and spring traps all need this; direct array
   pokes would duplicate the wake / `inv_inertia` handling. Joins the backend-parity
   test suite.

2. **`physics.KinematicAnimator`** — a per-frame driver for KINEMATIC bodies given a
   pose function `t -> (position, orientation)`. Backs "always running" elevators and
   rotating arms. (Joint-driven, triggered variants use the existing `Joint`/
   `JointDrive` and need no new code.)

3. **Fixed-offset follow-camera helper** (`move/followcam.py`) — given a target
   position and a fixed offset+look, write `ViewPlatform.position`/`quaternion`.
   Supports **holding the target** (freeze on the last square during a fall).
   Perspective projection (v1); generic for any overhead demo.

4. **HUD text overlay helper** — screen-space corner text for the countdown timer,
   speed, and material label, wrapping the existing atlas text
   (`scenegraph/text/shadertext.py`) + overlay pass. If an existing overlay suffices
   this collapses to demo-side glue.

5. **Pairwise friction override on `PhysicsWorld`** — the engine derives contact
   friction by combining the two materials' per-material `staticFriction`/
   `dynamicFriction` scalars through `frictionCombine` (AVERAGE/MIN/MAX/MULTIPLY).
   The demo needs an **explicit coefficient per marble↔surface pairing** (§7), which
   a single combine rule of per-material scalars can't express (e.g. rubber-on-stone
   grips but rubber-on-ice slips, independent of what steel does on either). Add an
   optional **pairwise μ table** the narrow-phase/solver consults first —
   `world.set_pair_friction(mat_a, mat_b, static_mu, dynamic_mu)` — falling back to
   the existing combine rule when a pair has no override. Small, generic, and
   testable against the solver.

Everything level- or game-specific (generator, marble rules, respawn, win/lose,
HUD content) stays in the demo package.

## 4. Procedural level generation

The generator is the heart of the demo and lands early (Phase 2). It produces a
**graph of track tiles** on an integer grid, then realizes each tile as physics +
render nodes through the piece vocabulary (§5).

- **Grid + path.** A level is a grid of unit cells at varying heights. A seeded RNG
  carves a **connected path** from a `start` cell to a `finish` cell — a random walk
  / drunkard's-walk biased toward the goal, with optional branches and dead-ends.
  Reproducible from `(seed, difficulty)`.
- **Elevation profile.** Cells step up/down along the path within a slope budget, so
  the track has the descending, terraced Marble-Madness feel. Larger drops become
  multi-cell ledges; some steps become **ramps** (Phase 4+).
- **Gaps.** The generator may omit cells to create **gaps** the marble must jump —
  always preceded by enough run-up (and later an upward ramp) that a well-steered
  marble can clear them. A solvability check (a coarse physics or ballistic estimate)
  rejects unfair layouts.
- **Track set / occupancy.** The set of occupied `(col,row)` cells and their heights
  is retained as the **track map**. This is what the fall-detector and camera-hold
  logic query (§5): "is the marble currently over a track cell, and near its
  surface?" This is what distinguishes a *jump* (airborne but still over/heading to
  track) from a *fall* (over the void).
- **Decoration pass (later phases).** Once basic generation works, secondary passes
  sprinkle walls along edges, bumpers on tight corners, boost ramps on straights,
  and mechanisms at chokepoints, each gated by difficulty.
- **Difficulty knob** scales grid size, path length, gap frequency, and mechanism
  density; it also sets the level's `time_limit` from an estimated traversal time.

Output is a `Level` (§5) — generation and hand-authoring produce the same structure,
so everything downstream is identical.

## 5. Level structure & the piece vocabulary

A `Level` is the generator's (or an author's) output: a track map plus a list of
typed **pieces**, each of which knows how to `build(scene)` — creating its
static/kinematic physics body and its PBR-shaded render node, and wiring any trigger
listener.

```python
Level(
    name="Generated-0007",
    seed=7, difficulty=2,
    time_limit=75.0,
    marble_start=(0, 1, 0),
    track_cells={(0,0):0.0, (1,0):-0.3, (2,0):-0.6, ...},   # occupancy + height
    kill_y=-8.0,
    respawn_delay=2.0,                                       # penalty before respawn
    surface="stone",
    pieces=[
        Floor(cell=(0,0)), Floor(cell=(1,0)), Ramp(cell=(4,0), angle=18, boost=4.0),
        Wall(edge=((3,0),'E')), Gap(cells=[(6,0),(7,0)]),
        Bumper(cell=(9,1), restitution=0.9),
        SpringTrap(cell=(11,0), impulse=(0,7,-3), rearm=1.5),
        Elevator(cell=(13,0), travel=(0,4,0), period=4.0),
        RotatingArm(cell=(15,0), length=3, rpm=20),
        Finish(cell=(18,0)),
    ],
)
```

**Track-presence & fall vs. jump** (the load-bearing rule):

- Each frame the controller finds the marble's `(col,row)` and asks the track map
  whether that cell is occupied and how far the marble is above/below its surface.
- **Grounded:** near a track cell's surface with a downward contact → this cell
  becomes the **checkpoint** (respawn point) and the **camera's held target**.
- **Jumping:** airborne but its ballistic path still lies over occupied cells (or it
  is rising / within jump range of track) → keep following with the camera, do *not*
  respawn.
- **Falling off:** over the void (no track cell under it) and descending, or below
  `kill_y` → enter the **respawn state**: freeze the camera on the last checkpoint
  square, let the marble keep falling out of view, and start a **penalty timer**
  (`respawn_delay`, e.g. ~2 s). Only when it elapses does the marble reappear at the
  checkpoint square with zeroed linear+angular velocity and control return. The level
  timer runs throughout, so a fall always costs time.

`kill_y` is the ultimate backstop; the track-occupancy test is what catches a
side-fall the instant it clears the edge, so the *detection* is immediate even
though the *respawn* is deliberately delayed. The delay also removes any incentive
to drop off the edge to shed momentum — it is strictly slower than staying on track.

## 6. Game mechanics — how each maps to the engine

| Mechanic | Implementation |
|---|---|
| **Marble** | Dynamic sphere `PhysicsBody`; `PBRMaterial` per material choice. Kept **awake every frame** (the world's sleep pass would otherwise park a momentarily-resting marble and zero its velocity) so gravity and steering always apply. |
| **Spin steering** | Arrow keys → `apply_angular_impulse` about the horizontal axis whose rolling contact pushes the marble in the camera-relative travel direction, + a small linear `apply_impulse` assist. Tunable spin:linear ratio. |
| **Jump off a ramp** | Emergent: the rigid body launches ballistically off an upward ramp when fast enough. No special code beyond *not* triggering fall-respawn while a jump is in progress (§5). |
| **Ramp → extra speed** | Angled static tile (low friction) with an overlapping **boost trigger**: on overlap, `apply_impulse` along the ramp's travel axis, capped to a max speed. |
| **Wall → speed kill** | Static box, low-restitution + high-friction material; a large normal contact impulse additionally clamps horizontal speed. |
| **Hard landing → speed kill** | Impact detector: contact normal impulse (or pre-contact downward speed) over a threshold on a non-elastic surface → damp linear speed toward zero. Elastic surfaces skip it. |
| **Rubber bumper → energy return** | High-restitution material; solver returns energy. Sprung bumpers add an extra outward `apply_impulse` on contact. |
| **Spring-loaded trap** | Static **trigger**; marble overlap fires `apply_impulse` (launch), one-shot or re-armed after a cooldown. |
| **Elevator** | KINEMATIC body moved vertically by `KinematicAnimator` (always running) or a prismatic `Joint` position-drive (triggered). |
| **Rotating arm** | KINEMATIC body spun by `KinematicAnimator` or a revolute `Joint` velocity-drive. |
| **Fall off → respawn** | Track-presence test (§5) → enter respawn state: camera holds the last checkpoint square, `respawn_delay` (~2 s) penalty elapses while the level timer keeps running, *then* teleport to that square with zeroed velocities. Delay prevents dropping off to shed momentum. `kill_y` backstop. |
| **Finish** | `Trigger` at the goal; overlap → win (stop timer, next level). |
| **Reset** | Key zeroes marble + timer and rebinds to level start (abort run). |
| **Timer** | Per-level `time_limit` counts down in the HUD; zero → lose. |

## 7. Marble material table

Each marble material pairs a **physics `Material`** with a **`PBRMaterial`**:

| Material | metallic | roughness | transmission | friction (s/d) | restitution | mass |
|---|---|---|---|---|---|---|
| **steel** | 1.0 | 0.15 | — | 0.4 / 0.3 | 0.15 | heavy |
| **chrome** | 1.0 | 0.03 | — | 0.35/0.28 | 0.1 | heavy |
| **glass** | 0.0 | 0.02 | ~0.9 | 0.3 / 0.25 | 0.2 | light |
| **rubber** | 0.0 | 0.7 | — | 1.0 / 0.9 | 0.8 | medium |
| **wood** | 0.0 | 0.8 | — | 0.5 / 0.4 | 0.2 | light |
| **ice** | 0.0 | 0.1 | — | 0.05/0.02 | 0.05 | medium |

A key cycles the marble material (look + feel change live). Surface materials
(stone, metal grate, rubber pad, ice sheet) reuse the same table for static pieces.
Glass uses the screen-space transmission path; if that costs too much fps on a fast
object, glass falls back to a low-roughness dielectric with high specular.

### Pairwise friction table

The per-material scalars above set gross feel, but **the coefficient that governs
how much spin becomes motion is defined per marble↔surface pairing**, through the
engine's pairwise-friction override (§3.5). This is a 2-D table
(marble material × surface material → static μ, dynamic μ). Illustrative dynamic μ:

| marble ＼ surface | stone | metal grate | rubber pad | ice |
|---|---|---|---|---|
| **steel**  | 0.35 | 0.30 | 0.55 | 0.03 |
| **chrome** | 0.30 | 0.28 | 0.50 | 0.02 |
| **glass**  | 0.28 | 0.25 | 0.45 | 0.04 |
| **rubber** | 0.90 | 0.75 | 1.10 | 0.15 |
| **wood**   | 0.50 | 0.45 | 0.70 | 0.08 |
| **ice**    | 0.10 | 0.08 | 0.20 | 0.02 |

Any pairing without an explicit entry falls back to the material-combine rule.
Values above are a starting point to tune during Phase 1 so each marble *feels*
distinct on each surface (a rubber marble bites and turns sharply; a steel marble on
ice barely responds and drifts).

### Coupled spin↔translation — emergent, not scripted

The two behaviours the control scheme relies on **fall out of the existing solver
for free** and are *not* special-cased in demo code — they come from the fact that
`physics/solver.py` applies friction as a tangential impulse **at the contact
point**: `_relative_velocity` includes the contact-point term `ω×r`, and every
friction impulse feeds back into `angular_velocity` through the lever arm
(`_skew_apply` = `invI · (r × P)`), Coulomb-clamped to `μ · normalImpulse`.

- **Spin slows as it imparts movement.** A marble whose contact point is slipping
  gets kinetic friction that *accelerates it forward and reduces its spin* until it
  reaches rolling-without-slipping (`v ≈ ω·r`). So spinning up and then rolling
  naturally trades angular for linear velocity — exactly the "the marble slows its
  spin as the spin imparts movement" behaviour, with no extra code.
- **Low→high friction transfers stored spin into a lurch.** On a low-μ surface
  (steel/glass on ice) the friction cap is small, so the marble can build up spin
  while barely translating — it slips and spins in place. The moment it rolls onto a
  high-μ surface (rubber pad, stone) the cap jumps, so the large stored slip velocity
  now drives a big tangential impulse: a **burst of forward momentum and a rapid
  spin-down**. This is precisely "when it transitions from a low-friction surface to
  a higher-friction one it changes how much momentum gets applied," and it is
  emergent once the *pairwise* μ (above) is the coefficient the solver sees.

What this means for the work: we **tune**, not write, these dynamics — the levers are
the pairwise μ table, the marble's **mass and rotational inertia** (sphere inertia
`2/5·m·r²`, auto-derived by the engine from shape+mass), and **damping**
(`linearDamping`/`angularDamping`/`quadraticDrag` on `Motion`) to model rolling
resistance and air drag so a rolling marble coasts to a stop instead of rolling
forever. Phase 1 validates the feel; the impact/wall speed-kill rules (§6) sit on
top of this, they don't replace it.

## 8. Phasing (basic gameplay first, then the bits — Red/Green TDD)

**Phase 0 — Scaffold & first roll.** Create the `marble-demo/` package (§9),
`pyproject.toml` + `oglc-marble` entry point, and a `run.py` that builds a
`DemoScene` with one flat floor and one steel sphere, installs the fixed-offset
follow-cam, and lets the arrow keys spin the marble around. *Deliverable: a marble
you can roll on a plane, on screen, camera following.*

**Phase 1 — Marble controller, camera & fall/respawn.** `MarbleController`: spin-
steer mapping, the track-presence test, checkpoint tracking, fall-vs-jump
distinction, respawn-on-fall, camera-hold-on-fall, reset key. Engine additions §3.1
(`apply_impulse`/`apply_angular_impulse`) and §3.3 (follow-cam) land here with tests.
*Deliverable: the marble drives, jumps over a hand-placed gap, and respawns when it
truly falls off — with the camera holding the last square.*

**Phase 2 — Procedural generator + basic playable level.** The generator (§4): grid,
seeded path, elevation, gaps, track map; the core pieces Floor/Wall/Finish/kill
plane; the countdown timer. *Deliverable: a generated, completable level with a
start, a finish, and a clock — the first genuinely playable build.*

**Phase 3 — Ramps, boosts, wall/landing speed rules.** Ramp pieces with boost
triggers, the wall-hit and hard-landing speed-kill detectors, and generator support
for placing ramps (including upward launch ramps before gaps). *Deliverable: speed
matters; ramps launch real jumps across generated gaps.*

**Phase 4 — Mechanisms.** Bumper, SpringTrap, Elevator, RotatingArm via
`KinematicAnimator` and `Joint`/`JointDrive` + trigger impulses; generator decoration
pass places them by difficulty. *Deliverable: a generated level whose mechanisms move
the marble.*

**Phase 5 — HUD, win/lose, material variety, multiple levels.** Full corner HUD
(timer top-right, speed, material), win/lose states, level progression (finish →
next generated seed), the marble-material cycle. *Deliverable: a full time-trial
loop across a sequence of generated levels.*

**Phase 6 — Reflective PBR polish.** `OPENGLCONTEXT_IBL=full` (procedural studio
probe) and/or an HDR sky, shadow maps, per-material PBR appearances, glass
transmission, bloom. Tune the look. *Deliverable: the reflective marble mirroring the
level and sky.*

**Phase 7 — Assets, packaging, tests, docs.** `ASSET-LICENSES.md`, `README.md`,
`LICENSE` (MIT source), any authored `.glb`/textures, the CI-capture test, a docs
page, and any generator tooling.

## 10. Testing

- **Headless unit tests** for game logic — steering vector mapping, track-presence /
  fall-vs-jump classification, the **respawn state machine** (grounded → falling →
  delay-elapsing → respawned; camera held and level timer still advancing throughout,
  control locked until the delay ends), checkpoint selection, impact speed-kill
  thresholds, timer countdown, win/lose transitions — against a real/mock
  `PhysicsWorld`, no window.
- **Generator tests** — determinism (same `(seed,difficulty)` → same level),
  connectivity (a path from start to finish always exists), and a **solvability**
  check (every gap has adequate run-up). Fuzz many seeds.
- **Engine additions** (`apply_impulse`, `apply_angular_impulse`,
  `KinematicAnimator`, follow-cam) get direct tests and join the backend-parity suite.
- **Visual-regression capture** like the other demos: run under
  `OPENGLCONTEXT_AUTO_EXIT_FRAMES` + `OPENGLCONTEXT_AUTO_EXIT_CAPTURE_DIR` with a
  fixed seed, compare against a reference image (percentage tolerance); pin shadow
  cascades / LOD for determinism.
- Full suite stays green (project rule).

## 11. Resolved decisions

1. **Steering feel — spin-primary with a small linear assist**, both exposed as
   tunables. Start here; refine the ratio during Phase 1.
2. **Generator style — grid random-walk** for now (simple, controllable). Revisit
   only if generated levels feel samey.
3. **Camera — perspective only** from the fixed offset. Faithful isometric/ortho
   replication is **not** a goal; the follow-cam helper's ortho projection is dropped
   from v1 scope (it can return later if ever wanted).
4. **Glass — cheap dielectric approximation first** (low-roughness, high specular);
   escalate to full screen-space transmission only if fps holds.
5. **Level source — generate only for v1.** A `.glb` level loader (importing static
   geometry + OMI physics, which the engine already reads) is wanted eventually but
   deferred; the generator is the sole source for now.
